一、一句话定位

一个完全在浏览器本地运行的脑损伤风险评估工具：输入头部受撞击时的 9 通道运动学时序，用 Transformer 编解码器预测脑组织各处的最大主应变（MPS），输出逐毫秒的 P95/Max 曲线与 512 个脑区簇的应变场，并配一个约 95 万点的 3D 脑模型做彩虹色可视化。

单位自检法（免费送的）

角加速度通道的标准差约 1000。如果你误把 deg/s² 喂进去，归一化后的 z 值会整体放大约 57 倍，表现为输入分布严重离群（|z| 普遍 > 10）。采完数据先看 z 值分布，比事后怀疑结果靠谱得多。

三、完整推理管线

STEP 0
输入校验
T ∈ [1,200]；buffer 长度必须 = T×9×4 字节
STEP 1
z-score 标准化
逐通道 (x−mean)/std，9 个常数写死在静态文件里
STEP 2
编码器 ×1
整段 [T,9] → memory [T,512]，之后固定不变
STEP 3
解码器 ×T
自回归逐毫秒生成，无 KV cache，200 ms 就是 200 次串行前向
STEP 4
后处理
反归一化 → expm1 → 截断负值 → 加权分位数

解码器究竟怎么跑（这是性能核心）

  1. 起始 token 是全零向量，不是学出来的 BOS embedding。
  2. 每步把当前完整前缀重新喂入：[BOS] → [BOS, y₁] → [BOS, y₁, y₂] …
  3. ONNX 图层面确认输入 tgt_input 形状为 [batch, tgt_len, 512]、输出恒为 [batch, 1, 512]——每次调用只产出一个时间步。
  4. 图里有一个 Trilu 算子，说明自注意力带因果掩码（第 t 步只能看到 ≤ t 的历史）。
  5. 没有 KV cache，第 t 步要重算整个前缀，总计算量约 O(T²)。
  6. 关键细节：运动学只通过 memory 影响解码，解码器自己看不到 9 通道原始数据。

后处理三步（最容易漏、且漏了不报错）

// 1. 反归一化   2. expm1   3. 截断到非负
const v = Math.max(0, Math.expm1(y[t*512 + e] * stdY[e] + meanY[e]));

三个坑

  • 模型预测的是 log1p(MPS) 再做 z-score，反变换必须是 exp(x)−1，且顺序是先反归一化再 expm1。
  • Math.max(0, …) 的截断会改变分位数结果，不能省。
  • P95 不是普通百分位，而是按网格单元数加权的分位数：权重来自 belong2.u16（118,840 个单元映射到 512 簇），比较时用 Math.ceil(q × total) 累计权重。直接对 512 个簇值取第 95 百分位会得到不同的数。

六、迁移边界：这六个问题，网站能回答几个

#问题能否得知结论
1传感器型号❌ 不能网站不接触任何传感器
2采样率是否 1 ms⚠️ 只规定输入网格必须 1 行 = 1 ms；传感器原生率自由，重采样归你
3蓝牙通信协议❌ 完全不能全站零 BLE / GATT 代码
4九通道顺序与单位✅ 完全定义见第二节，规格明确
5撞击时刻判断方式❌ 不能无触发、无阈值；网站只接受"已经切好的窗口"
6截取窗口前后时长⚠️ 只规定总长上限≤ 200 ms 是硬约束，前后如何分配完全自由

判定依据可复现：对主包与 Worker 全文检索 bluetooth / gatt / serial / sensor / trigger / threshold / impact 命中数均为 0（个别命中是 enable、table、window 的子串误报）。

附带查出一件事：网站自带的"Download example"是假的参考数据

那两个按钮是在浏览器里现场合成文件，站点上根本没有样例数据集（直接请求 URL 返回 404，HDF5 由 WASM 即时写出）。硬编码的示例只有 3 毫秒、27 个数，其中 lin_acc_z ≈ 9.81（就是重力），角速度才 0.1 rad/s——完全不是撞击数据。

所以：可以用来测链路连通性（返回的 sampleCount 应为 3），但千万别拿它做精度验证。

七、工程上最容易踩的四个点

  1. 多线程 WASM 需要 crossOriginIsolated——它要求页面处于安全上下文且服务端返回 COOP: same-origin + COEP: require-corp。App 里若用 file:// / asset:// 直接加载本地资源，通常拿不到该标志 → 线程数被锁为 1。而解码器是 200 次串行前向，单线程必卡。解法：App 内起本地 HTTP 服务，或让 WebView 拦截请求补上这两个响应头。
  2. 安卓 WebView / 鸿蒙 ArkWeb 通常拿不到 WebGPU，会回退到 WASM。回退本身改变数值路径，所以对比实验里必须记录 backend 字段。
  3. 浮点差异是存在的，但不是 bug——桌面/移动 WebGPU、桌面 WASM、ARM NEON、部分设备 FP16 加速，结果会有 1e-6 ~ 1e-3 量级的相对差异。必须量化，不能默认"应该一样"。
  4. 窗口起点偏移会改变整条 MPS 曲线（因为是整段自回归生成），但"撞击点落在窗口内哪个位置"这个训练约定无法从静态资源推断，是当前风险最高的未知项。

八、待确认项（必须问老师）

优先级事项
最高窗口对齐约定：撞击时刻在窗口内的相对位置。建议做敏感性实验——同一段数据把窗口起点平移 −20/−10/0/+10/+20 ms 各跑一次，看 Peak P95 与峰值时刻的变化幅度。
最高传感器佩戴朝向与模型的头部解剖坐标系对齐关系。对不齐 XYZ 就错位，结果直接是错的。
中训练时是否对输入做过滤波（如低通）。若无从得知，手机端不要额外加滤波，与网站输入保持同一处理。
中传感器的 BLE 服务/特征 UUID、最大包率、直出字段与单位（deg/s 还是 rad/s、g 还是 m/s²）、数据交付方式（BLE 通知还是厂家 SDK）。
低模型训练数据来源、样本量、是否含儿童/成人差异（若开题需说明模型可信度）。
